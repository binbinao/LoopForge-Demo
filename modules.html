Core Concepts

六大核心能力

LoopForge 把「一条需求变成可交付的代码」拆成六个互相咬合的部分。理解每一块的职责边界与协作关系，就掌握了整个平台的工作骨架。

1. 工作区 Workspace

工作区是会话绑定的沙箱环境，是 Agent 真正动手的地方。文件读写、命令执行、构建、测试都发生在里面，平台按本轮发言人的个人凭证配好 Git 与 GitHub 访问。

隔离与可恢复

每个会话有自己的沙箱与文件快照，切走或空闲回收后能恢复现场；开区默认是空目录，仓库自己 clone。

按需选环境

按任务需要的语言与工具链选择运行环境（如通用 Docker、原生沙箱），环境不对就切，而不是硬凑。

关键约定

  • 不预先检出仓库：进入工作区后自己 git clone、建分支、checkout，平台不会替你准备代码。
  • 凭证已就位：HTTPS 走 Git Token、SSH 走个人密钥，GH_TOKEN 可用于 API 调用；令牌不落盘、不打印。
  • 产物可交付：报告、HTML demo 等文件可以直接发布到对话里，链接与侧栏浏览器共享同一台执行机。
常见误区：把工作区当成「只读预览器」。它同时是执行环境——构建、跑测试、起本地服务都在这里完成，改完再看结果。

2. SOP 工作流

SOP 把一条需求从定型到交付串成可编排的节点链路。每个节点有自己的输入、产物与通过标准，关键节点由人把关，过程全程可追溯。

  • 节点化：需求定型 → 方案设计 → 开发实现 → 独立评审 → 测试验证 → 人工验收 → 发起 MR → 交付汇总。
  • 产物沉淀：每个节点都产出可查阅的产物文件，后续节点基于产物推进，而不是靠上下文口头传递。
  • 可暂停可续跑：运行可以停下、恢复，改完代码回到后续节点重跑，不必从头再来。

什么时候该走 SOP：要落到仓库的新需求或新功能、需要多人多环节协作、或交付物需要留痕。细节见 交付流程。

3. 角色与子 Agent

评审、测试等角色可以作为独立子 Agent 被派发，拥有自己的上下文与工具，与「做的人」相互独立。

独立评审

只看改动与风险点，不受实现思路影响，给出可核对的结论。

整套测试

按仓库指令跑用例、复现问题，用真实输出说话。

并行协作

互不依赖的几块工作同时派发，缩短整体耗时。

什么时候派角色：整件事就是某个角色的本职、工作量不小，或改动碰到资金/积分、并发、鉴权权限、数据迁移、对外接口这类出错代价高的地方。

4. 技能 Skills

技能把专项能力打包成可复用说明：任务与技能描述匹配时加载，按它的步骤执行即可，不需要额外确认。

  • 按需加载：只在任务对得上时引入，避免无关流程拖慢执行。
  • 能力复用：格式转换、文档生成、检索分析等，一次封装、反复使用。
  • 开箱即用：加载即生效，不需要改仓库配置。

5. 需求管理 Issues

需求是 LoopForge 的工作单元：从 backlog 一路走到完成，关联仓库、绑定 SOP、派发运行、跟踪 MR 合入状态。

阶段做什么
backlog记录想法与范围，关联目标仓库
todo / in_progress定型需求、派发运行，进入实现
in_review评审与测试，处理发现的问题
done / closedMR 合入、交付汇总、关闭需求

6. Git 与 MR 交付

克隆、建分支、提交、推送、开 MR 由 Agent 自己完成；开好的 PR/MR 会自动登记到需求并跟踪合入，不需要手动回填。

git clone <repo-url> && cd <repo>
git checkout -b feat/your-change
# 改动 + 验证
git add -A && git commit -m "feat: your change"
git push -u origin feat/your-change
# 开 PR（gh 或 GitHub API）
安全边界：推主分支、强推、合并 PR 这类不可撤销操作，只在用户明确要求时执行；平时一律走分支 + PR。
