Quick Start

四步开始你的第一次交付

从建分支到开 PR，这套节奏可以复用在每一个需求上。下面每一步都给出真实命令和验证方式，照做即可。

1. 打开工作区

工作区是会话绑定的沙箱环境。进去后先确认语言与工具链齐备，再开始动手——工作区默认是空目录，不会替你检出代码。

  • 拿到的是真实终端与文件系统，可以跑构建、跑测试、起本地服务。
  • Git 与 GitHub 凭证已配好，可以直接 clone 与 push。
  • 会话结束或空闲回收后，文件快照可以恢复，不必重来。

2. 克隆并建分支

永远在功能分支上工作，主线保持干净。

git clone https://github.com/<owner>/<repo>.git
cd <repo>
git checkout -b feat/<short-name>

先读仓库里的说明文件（README、CONTRIBUTING、构建脚本），确认测试怎么跑，再动代码。

3. 改动并验证

改动尽量小而聚焦，一次 commit 一件事。改完必须验证：跑与改动相关的测试、本地起服务看实际效果，用输出作为证据。

# 示例：静态站点本地预览
python3 -m http.server 8080
# 打开 http://localhost:8080 逐个点开导航与页面检查
验证标准：能说清「改了什么、怎么验的、结果如何」。只跑过一条命令就宣称通过，不算验证。

4. 推送并开 PR

git add -A
git commit -m "feat: <一句话说明>"
git push -u origin feat/<short-name>

# 用 gh
gh pr create --base main --head feat/<short-name> \
  --title "feat: <标题>" --body "<改动与验证说明>"

没有 gh 时同样可以用 GitHub API 开 PR。开好的 PR 会自动登记到需求并跟踪合入，不需要你手动回填。

边界：推主分支、强推、合并 PR 只在明确要求时执行；默认走「分支 + PR + 由你合并」。

实战案例：从零搭建个人工作台

目标：把上面的四步流程走成一次完整闭环，在本地做出一个可预览的个人工作台示例页。下面每一步都有明确产出和验证方式，照着做一遍即可。

案例产物

这个示例只做三个最小模块，采用原生 HTML / CSS / JavaScript，数据保存在浏览器 localStorage。它是教学示例，不需要在本仓库中真正实现应用代码。

待办清单

新增、勾选完成、删除待办，刷新后仍保留。

快速笔记

一页随手记录，输入后自动保存到本地浏览器。

常用链接

集中放几个常用入口，点击即可在新标签页打开。

操作步骤

  1. 新建需求

    在 LoopForge 新建需求 Issue，写清目标与验收标准（三个模块可用、刷新后数据仍在、窄屏可读），并关联目标仓库。产出：一条可追溯的需求，后续提交与 PR 都围绕它展开。

  2. 打开工作区并建分支

    进入工作区，克隆目标仓库并新建功能分支；先读一遍 README 和构建说明再动手。产出：干净的工作区和独立分支。

    git clone https://github.com/<owner>/<repo>.git
cd <repo>
git checkout -b feat/personal-dashboard

  3. 确定实现方案

    列出页面文件清单（例如 index.html、styles.css、app.js）与三个模块的划分，明确数据统一存 localStorage，不引入外部依赖。产出：一份可执行的最小方案，交由人确认后再开工。

  4. 让 Agent 实现页面与交互

    按方案让 Agent 实现待办增删改、笔记保存与链接跳转，边改边本地预览；人负责判断界面与交互是否符合预期。产出：可运行的静态页面，不在此处贴真实应用代码。

  5. 本地验证并留下证据

    启动静态服务，逐项点验三个模块与窄屏表现，再按「改了什么 / 怎么验的 / 结果如何」整理证据。产出：一段可复述的验证记录，而不是一句「已完成」。

    python3 -m http.server 8080
# 打开 http://localhost:8080 逐项点验待办、笔记与常用链接

  6. 派角色复核（可选）

    派评审或测试子 Agent 检查可访问性与窄屏表现：标题层级、键盘焦点、375px 下是否溢出。人核对具体依据再决定是否调整，不只转述结论。

  7. 提交、推送并开 MR

    把改动提交到功能分支并推送，再用 gh 开 MR，描述里附上上一步的证据。产出：一个可被复核的 MR，平台会自动把它登记到需求，无需手动回填。

    git add -A
git commit -m "feat: <一句话说明>"
git push -u origin feat/personal-dashboard

# 用 gh 开 MR
gh pr create --base main --head feat/personal-dashboard \
  --title "feat: <标题>" --body "<改动与验证说明>"
边界：不直推 main、不强推、不自行合并 PR；默认走「分支 + PR + 由你合并」，合并动作由人完成。

上线检查清单

检查项通过标准
分支隔离改动只在功能分支，main 未被直推
构建/测试与改动相关的命令全部通过
线上效果本地预览或部署后逐页点开，无 404、无死链
移动端窄屏下导航可展开、可跳转
PR 描述写清改了什么、怎么验证、影响面

常见坑

点导航没反应？

先确认链接指向的目标页面或锚点真的存在。锚点 #id 需要有对应 id 的元素；多页站点则要确认子页面文件已经提交并部署。

线上和本地不一致？

静态站点常常是缓存或构建产物未更新：确认分支已合并、构建已跑完，再用无痕窗口访问。

样式在窄屏错乱？

检查媒体查询里是否把导航隐藏了却没给出替代入口——隐藏导航必须配一个可用的菜单按钮。
